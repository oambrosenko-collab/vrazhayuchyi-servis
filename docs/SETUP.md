# Налаштування

## Supabase

Проєкт: **vrazhayuchyi-servis**, регіон `eu-central-1` (Франкфурт), ref `bgyjpjdrjscfdrfrgdqd`.
Франкфурт, а не дефолтний регіон, бо затримка до України ~30 мс замість ~280 мс —
на мобільному 4G це помітно в плеєрі.

## Локальний запуск

```bash
npm install
cp .env.example .env.local   # заповнити значення з дешборду Supabase
npm run dev
```

`.env.local` уже лежить у репозиторії незакомічений (`.gitignore` ріже `.env*`).
Якщо його немає — ключі тут: Supabase → Project Settings → API keys.

| Змінна | Звідки |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Project Settings → API |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | Project Settings → API keys → publishable |
| `NEXT_PUBLIC_SITE_URL` | `http://localhost:3000` локально, домен на проді |
| `DATABASE_URL` | Project Settings → Database → Connection string (потрібен лише для `drizzle-kit`) |

**Redirect URL.** Щоб magic link повертав у застосунок, у Supabase →
Authentication → URL Configuration додай `http://localhost:3000/auth/callback*`
і той самий шлях для продового домену. Без цього лист прийде, а перехід впаде.
Зірочка обовʼязкова: ми передаємо `?next=`, і без вайлдкарда адреса не збігається.

**Шаблони листів — обовʼязкова ручна правка.** Дефолтні шаблони Supabase
кладуть у лист `{{ .ConfirmationURL }}`, тобто PKCE-код. PKCE привʼязує
посилання до браузера, який його запитав, через куку `code_verifier` — і це
ламає найзвичайніший шлях офіціанта: управляючий кидає інвайт у робочий чат,
офіціант відкриває його у вбудованому браузері Telegram, вводить пошту, потім
відкриває лист у застосунку Gmail — а це вже інший браузер. Той самий телефон,
та сама людина, мертве посилання.

Тому `/auth/callback` приймає `token_hash` і перевіряє його через `verifyOtp`.
`code` він теж приймає — як запасний шлях, поки шаблон дефолтний.

**Заблоковано до підключення SMTP.** Supabase не дає редагувати шаблони, поки
не підʼєднаний власний SMTP: на сторінці Authentication → Emails висить
«Set up custom SMTP to edit templates». Тобто поки відправник вбудований,
листи йдуть зі стоковим шаблоном і несуть `code`, з усіма обмеженнями PKCE.

Коли Resend буде підключений, обидва шаблони (**Confirm signup** і
**Magic Link**) мають посилатись на:

    {{ .RedirectTo }}&token_hash={{ .TokenHash }}&type=email

`.RedirectTo` — це те, що код передав у `emailRedirectTo`, разом із `?next=`.
Саме тому далі йде `&`, а не `?`. Якщо колись заберуть `?next=` з
`sendMagicLink`, цей амперсанд зламає адресу.

Шаблонів два, бо `signInWithOtp` шле **Confirm signup** новому користувачу
й **Magic Link** наявному. Офіціанти майже завжди нові, тож перший важливіший.

## Міграції

Схема живе в `supabase/migrations/*.sql` і застосована на віддаленому проєкті.
Пишемо міграції як SQL, а не через `drizzle-kit generate`: RLS-політики,
security-definer функції та гранти не мають еквівалента в Drizzle, а саме їх
треба читати порядково.

`src/db/schema.ts` — дзеркало для типізованих запитів. `drizzle-kit push`
не запускати ніколи, тільки `check`.

Після будь-якої міграції перегенерувати типи:

```bash
npm run db:types
```

## Тести — обовʼязкові перед кожним релізом

```bash
npm run db:test
```

Шість файлів. `rls_isolation.sql` — два заклади, спроба прочитати чужі дані.
`course_access.sql` — доступ до уроків і чесність прогресу: прострочений
заклад, звільнене місце, правило 90%, спроба накрутити залік перемоткою.
`team_report.sql` — звіт для адміна: не протікає між закладами, недоступний
співробітнику, звільнене місце зберігає цифри. `quiz_and_certificate.sql` —
недосяжність правильних відповідей, підрахунок балів, видача сертифіката.
`superadmin.sql` — область власника платформи: адмін закладу й офіціант
не дістають жодної `su_`-функції, власник не займає місця й не рахується
учнем. `webinars.sql` — розклад і відвідування: чернетка не видна нікому,
крім власника, прострочений заклад втрачає архів, посилання на ефір зникає
після завершення, а звіт рахує лише ті вебінари, що були після приєднання
людини. Кожен рядок має бути `PASS`.
Тест сідає дані й відкочує транзакцію, тож нічого по собі не лишає —
але ганяти його все одно краще на гілці, не на проді.

Обидва скрипти (`db:types`, `db:test:rls`) потребують Supabase CLI:
`brew install supabase/tap/supabase`.

## Чому немає демо-акаунта з паролем

Спокусливо засіяти акаунт із паролем, щоб не чекати на лист. Не роби цього:
`publishable key` публічний за задумом, вхід за паролем у Supabase увімкнений
за замовчуванням, і пароль у репозиторії портфоліо означає, що будь-хто
заходить у живий проєкт як `org_admin`. Вхід за magic link працює — ним і
користуйся.

Коли знадобиться демо-доступ для сторонніх (рекрутер відкриває посилання й
дивиться), це окреме свідоме рішення з окремим обмеженим акаунтом, а не
забутий seed. У PRD для цього вже передбачений вхід із паролем для адміна
закладу на `/login`.

## Створити заклад руками

Перші клієнти отримують доступ так — дві хвилини замість двох тижнів модуля оплат.

```sql
select o.name,
       'https://ТВІЙ-ДОМЕН/join/' || o.invite_token as invite_url,
       o.expires_at::date
from app.provision_organization('Назва закладу', 25, 'owner@example.com', 12) o;
```

`admin_email` тут важливий: перша людина, яка зайде за лінком із цією поштою,
автоматично стає `org_admin` і бачить кабінет. Решта — `employee`.

| Шлях | Стан |

## Три ролі

| Роль | Де живе | Що бачить |
|---|---|---|
| `employee` | `/learn` | Свій курс і свій прогрес. Нічого про колег |
| `org_admin` | `/admin` | Свій заклад: команда, прогрес, інвайт-лінк, звільнення місця |
| `superadmin` | `/su` | Усі заклади, весь контент, ключ відповідей до тестів |

`superadmin` існує в enum і в RLS від кроку 1 — екрани зʼявились тільки
зараз. Сторінки під `/su` віддають **404**, а не 403: тому, хто не власник,
не треба знати, що ця область узагалі існує. Кожна `su_`-функція додатково
перевіряє роль усередині себе — guard у layout зупиняє цікавого, перевірка
в функції зупиняє того, хто кличе RPC напряму.

**Власник — не учень.** Суперадмін може бути прикріплений до закладу (так
зручно переглядати), але не займає місця в пакеті, не потрапляє у звіт для
адміна й не впливає на середній прогрес. Без цього правила два екрани
показували 37% і 31% для тих самих людей.

## Чому `/su` не вміє частини того, що в PRD

- **Виручка й заявки на рахунки** — немає таблиці `orders`, це крок «Оплата».
- **Заливка відео** — Bunny не підключений. Поле `bunny_video_id` у формі
  уроку є; поки воно порожнє, урок показує плеєр-заглушку.
- **Вебінари** — таблиці немає взагалі.

Видалити урок, який хтось уже дивився, не можна: `lesson_progress` піде
каскадом і зі звіту власника зникнуть дані, які там уже бачили. Замість
цього курс знімається з публікації.

## Чому тест живе за адресою `/learn/quiz/[quiz]`, а не `/learn/[module]/quiz`

Карта сторінок у PRD пропонує друге, але в App Router два різні динамічні
параметри на одному рівні (`[lesson]` і `[module]`) не збираються. До того ж
фінальний тест не належить жодному модулю, і при схемі з модулем йому
довелося б робити окремий маршрут. Один маршрут по id тесту покриває обидва
випадки.

## Відповіді на тести не існують для браузера

`quiz_questions` і `quiz_options` не мають **жодного** granta для
`authenticated`. Не політики, яка ховає колонку — RLS працює на рівні рядка,
і `is_correct` поїхав би разом із ним. Питання видно лише через
`quiz_sheet()`, яка цю колонку не вибирає, а оцінює тільки
`submit_quiz_attempt()` на сервері.

Supabase-лінтер позначає ці дві таблиці як «RLS enabled, no policies», рівень
INFO. Це не недогляд: відсутність політик за відсутності granta означає, що
таблиця запечатана повністю. Додавати туди політику не треба.

## Сертифікат

PDF генерується на запит із рядка в `certificates`, а не зберігається файлом.
Імʼя й назва закладу **скопійовані** в рядок на момент видачі: перейменування
ресторану через рік не має переписувати документ, який людина вже завантажила.

Номер (`VS-2026-00001`) є з першого дня, хоча публічна сторінка верифікації
`/cert/[number]` — це v1.1. Дешевше тримати номер одразу, ніж дописувати його
потім до вже виданих сертифікатів.

Шрифт Roboto лежить у `public/fonts/` і вбудовується в PDF. Вбудована в PDF
Helvetica не має кирилиці, і без власного шрифту імена рендерились би
порожнечею — мовчки, без жодної помилки.

## Що означає «остання активність»

Не останній вхід, а **останній переглянутий урок**. `users.last_seen_at`
проставляється в `save_lesson_progress` і лише тоді, коли beat ніс реальне
відтворення — пауза на відкритій вкладці не тримає людину «активною».

Так зроблено свідомо: власнику потрібен сигнал «тиждень нічого не дивився»,
а не «заходив і вийшов». Якщо колись знадобиться саме останній вхід — це
окреме поле, а не перевизначення цього.

## Відео — заглушка, і чому саме так

Реального відео ще немає, тому `StubPlayer` ганяє той самий годинник від
таймера. Це не макет: позиція зберігається, час перегляду накопичується,
урок зараховується на 90%, перемотка не зараховується. Уся логіка, яка
має значення, працює по-справжньому.

Підключення Bunny Stream — це **заміна одного компонента**. Контракт у
`PlayerProps`: отримати `durationSec` і `initialPositionSec`, викликати
`onTick(position, delta)` раз на секунду реального відтворення. Хук
`useProgress` і сервер не змінюються взагалі.

Одна річ, яку легко зламати при заміні: `delta` — це **реально відтворені
секунди**, а не стрибок позиції. Якщо нова реалізація почне віддавати
різницю позицій, перемотка в кінець зарахує урок, і звіт для власника
перетвориться на фікцію.

## Архітектурне рішення, яке варто знати до першої правки

Клієнт має **тільки SELECT** на `organizations` і `users`. Жодної
INSERT/UPDATE/DELETE політики не існує. Усі записи йдуть через
security-definer функції: `join_organization`, `release_seat`,
`regenerate_invite`, `su_provision_organization`.

Так зроблено свідомо: підроблений payload не має куди дійти, а вся логіка
місць (включно з блокуванням рядка організації, щоб двоє не зайняли одне
останнє місце) живе в одному місці, а не розмазана між політиками й кодом.

Якщо знадобиться новий запис — додавай RPC, а не політику на запис.
