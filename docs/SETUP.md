# Налаштування

## Supabase

Проєкт: **vrazhayuchyi-servis**, регіон `eu-central-1` (Франкфурт), ref `bgyjpjdrjscfdrfrgdqd`.
Франкфурт, а не дефолтний регіон, бо затримка до України ~30 мс замість ~280 мс —

## Локальний запуск

```bash
npm install
cp .env.example .env.local   # заповнити значення з дешборду Supabase
npm run dev
```

`.env.local` уже лежить у репозиторії незакомічений (`.gitignore` ріже `.env*`).
Якщо його немає — ключі тут: Supabase → Project Settings → API keys.

| Змінна | Звідки |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Project Settings → API |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | Project Settings → API keys → publishable |
| `NEXT_PUBLIC_SITE_URL` | `http://localhost:3000` локально, домен на проді |
| `DATABASE_URL` | Project Settings → Database → Connection string (потрібен лише для `drizzle-kit`) |

**Redirect URL.** Щоб magic link повертав у застосунок, у Supabase →
Authentication → URL Configuration додай `http://localhost:3000/auth/callback*`
і той самий шлях для продового домену. Без цього лист прийде, а перехід впаде.
Зірочка обовʼязкова: ми передаємо `?next=`, і без вайлдкарда адреса не збігається.

**Шаблони листів — обовʼязкова ручна правка.** Дефолтні шаблони Supabase
кладуть у лист `{{ .ConfirmationURL }}`, тобто PKCE-код. PKCE привʼязує
посилання до браузера, який його запитав, через куку `code_verifier` — і це
ламає найзвичайніший шлях офіціанта: управляючий кидає інвайт у робочий чат,
офіціант відкриває його у вбудованому браузері Telegram, вводить пошту, потім
відкриває лист у застосунку Gmail — а це вже інший браузер. Той самий телефон,
та сама людина, мертве посилання.

Тому `/auth/callback` приймає `token_hash` і перевіряє його через `verifyOtp`.
`code` він теж приймає — як запасний шлях, поки шаблон дефолтний.

**Заблоковано до підключення SMTP.** Supabase не дає редагувати шаблони, поки
не підʼєднаний власний SMTP: на сторінці Authentication → Emails висить
«Set up custom SMTP to edit templates». Тобто поки відправник вбудований,
листи йдуть зі стоковим шаблоном і несуть `code`, з усіма обмеженнями PKCE.

Коли Resend буде підключений, обидва шаблони (**Confirm signup** і
**Magic Link**) мають посилатись на:

    {{ .RedirectTo }}&token_hash={{ .TokenHash }}&type=email

`.RedirectTo` — це те, що код передав у `emailRedirectTo`, разом із `?next=`.
Саме тому далі йде `&`, а не `?`. Якщо колись заберуть `?next=` з
`sendMagicLink`, цей амперсанд зламає адресу.

Шаблонів два, бо `signInWithOtp` шле **Confirm signup** новому користувачу
й **Magic Link** наявному. Офіціанти майже завжди нові, тож перший важливіший.

## Шрифт Fixel

Зараз браузер підставляє системний — файлів немає, і це видно як два 404 у консолі.

1. Завантажити з [fixel.macpaw.com](https://fixel.macpaw.com)
2. Покласти в `public/fonts/`
3. Звірити імена з тими, що в `src/app/design-tokens.css`:
   `FixelDisplay-Variable.woff2`, `FixelText-Variable.woff2`

## Міграції

Схема живе в `supabase/migrations/*.sql` і застосована на віддаленому проєкті.
Пишемо міграції як SQL, а не через `drizzle-kit generate`: RLS-політики,
security-definer функції та гранти не мають еквівалента в Drizzle, а саме їх
треба читати порядково.

`src/db/schema.ts` — дзеркало для типізованих запитів. `drizzle-kit push`
не запускати ніколи, тільки `check`.

Після будь-якої міграції перегенерувати типи:

```bash
npm run db:types
```

## Тест ізоляції — обовʼязковий перед кожним релізом

```bash
npm run db:test:rls
```

Два заклади, спроба прочитати чужі дані. Кожен рядок має бути `PASS`.
Тест сідає дані й відкочує транзакцію, тож нічого по собі не лишає —
але ганяти його все одно краще на гілці, не на проді.

Обидва скрипти (`db:types`, `db:test:rls`) потребують Supabase CLI:
`brew install supabase/tap/supabase`.

## Чому немає демо-акаунта з паролем

Спокусливо засіяти акаунт із паролем, щоб не чекати на лист. Не роби цього:
`publishable key` публічний за задумом, вхід за паролем у Supabase увімкнений
за замовчуванням, і пароль у репозиторії портфоліо означає, що будь-хто
заходить у живий проєкт як `org_admin`. Вхід за magic link працює — ним і
користуйся.

Коли знадобиться демо-доступ для сторонніх (рекрутер відкриває посилання й
дивиться), це окреме свідоме рішення з окремим обмеженим акаунтом, а не
забутий seed. У PRD для цього вже передбачений вхід із паролем для адміна
закладу на `/login`.

## Створити заклад руками

Перші клієнти отримують доступ так — дві хвилини замість двох тижнів модуля оплат.

```sql
select o.name,
       'https://ТВІЙ-ДОМЕН/join/' || o.invite_token as invite_url,
       o.expires_at::date
from app.provision_organization('Назва закладу', 25, 'owner@example.com', 12) o;
```

`admin_email` тут важливий: перша людина, яка зайде за лінком із цією поштою,
автоматично стає `org_admin` і бачить кабінет. Решта — `employee`.

## Що вже працює

| Шлях | Стан |
|---|---|
| `/join/[token]` | Прев'ю закладу → magic link → імʼя → місце зайняте. Стани: недійсний лінк, місця закінчились, доступ минув, призупинено |
| `/login` | Magic link, без пароля |
| `/auth/callback` | Перевірка `token_hash` через `verifyOtp`, працює з будь-якого браузера, захист від open redirect |
| `/learn` | Заглушка під курс. Банер, якщо доступ закладу минув |
| `/admin` | Місця зайнято/вільно, дата кінця, інвайт-лінк із копіюванням і перегенерацією, команда, звільнення місця, вкладка «Історія» |
| `/access-revoked` | Екран для звільненого співробітника |

Чого ще немає: лендінг, `/pricing`, `/checkout`, `/su`, експорт CSV, листи.

## Архітектурне рішення, яке варто знати до першої правки

Клієнт має **тільки SELECT** на `organizations` і `users`. Жодної
INSERT/UPDATE/DELETE політики не існує. Усі записи йдуть через
security-definer функції: `join_organization`, `release_seat`,
`regenerate_invite`, `su_provision_organization`.

Так зроблено свідомо: підроблений payload не має куди дійти, а вся логіка
місць (включно з блокуванням рядка організації, щоб двоє не зайняли одне
останнє місце) живе в одному місці, а не розмазана між політиками й кодом.

Якщо знадобиться новий запис — додавай RPC, а не політику на запис.
